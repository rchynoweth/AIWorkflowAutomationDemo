# Data Model — Loan Servicing Intelligence

> **Synthetic data model.** This schema is a generic illustration designed for the demonstration. It does not
> represent any lender's production schema. Every table that carries source data includes `synthetic_data`.

Unity Catalog location (default): `main.loan_servicing_intelligence`. Locally the same logical tables are held
as pandas DataFrames, with operational state persisted under `data/processed/state`.

## 1. Synthetic source exports (`data/generated`, landed to the volume)

Generated by `src/data_generation/generator.py` with seed `20261012` and processing date `2026-10-12`.
Names are obviously synthetic (`Synthetic Borrower 0001`, `Synthetic Specialist 01`, `Synthetic Legal Vendor 01`).
Addresses, cities, counties, and postal codes are synthetic tokens (`Synthetic Address 0001`, `SYN01`), not
real places; state codes are generic two-letter codes used only for grouping.

## 2. Bronze (raw, lineage-preserving)

Tables: `bronze_loans`, `bronze_loan_events`, `bronze_milestone_rules`, `bronze_servicing_specialists`,
`bronze_attorneys_vendors`, `bronze_servicing_action_history`, `bronze_reviewer_decisions`.

All source columns are stored as **strings exactly as received**, plus:

| Column | Description |
|--------|-------------|
| source_file | File name (and volume path in Databricks) |
| ingested_at | UTC ingestion timestamp |
| batch_id | `BATCH-<yyyymmddHHMMSS>` per ingestion run |
| record_hash | SHA-256 of the pipe-joined source values |
| source_row_number | 1-based row number within the file |

Writes are append-only in production; demo mode overwrites to keep reruns idempotent.

## 3. Silver (typed, validated, standardized)

| Table | Key | Processing |
|-------|-----|-----------|
| silver_loans | loan_id | Types, upper-case codes, trims, latest-row dedup, `is_active`, joins specialist/party names and status, `dq_issues` |
| silver_loan_events | event_id | Types; System-of-Record overlay (adapter rows visible for the current cycle); dedup by latest `updated_at`; `milestone_sequence` join; per-loan `event_sequence`; `is_open`; `is_followup_type`; `dq_issues` |
| silver_milestone_rules | milestone_type | Types; `active` flag retained (engine uses active rules only) |
| silver_servicing_specialists | specialist_id | Types, active flag |
| silver_attorneys_vendors | party_id | Types, active flag |
| silver_active_foreclosures | loan_id | Active loans with `foreclosure_status <> NONE` and their current milestone |
| silver_servicing_action_history | action_id | Types; union of source history and `ops_actions` (app) |
| silver_reviewer_decisions | decision_id | Types; union of source history and `ops_reviewer_decisions` |

`dq_issues` is a semicolon-separated list of codes: `INVALID_DATE:<col>`, `INVALID_NUMBER:<col>`,
`UNKNOWN_CODE:<col>`, `MISSING_REQUIRED:<col>`, `COMPLETED_BEFORE_EVENT`, `COMPLETED_WITHOUT_DATE`,
`OPEN_WITH_COMPLETED_DATE`.

## 6. Relationships

```text
loans 1─* loan_events (loan_id)
milestone_rules 1─* loan_events (milestone_type)
servicing_specialists 1─* loans (assigned_specialist_id)
attorneys_vendors 1─* loans (assigned_attorney_vendor_id)
loans 1─* ops_recommendations 1─* ops_reviewer_decisions
ops_recommendations 1─0..1 ops_actions 1─* sor_servicing_events (action_id)
ops_actions 1─* ops_verification_results
```

## 7. Data quality

Silver never drops rows silently: invalid values become null with a `dq_issues` code, and loans whose current
milestone carries DQ issues raise `DATA_EXCEPTION` (RULE-DATA-005). Duplicate source rows are resolved by
latest `updated_at` (events) or last occurrence (other tables) and counted in pipeline logs.
